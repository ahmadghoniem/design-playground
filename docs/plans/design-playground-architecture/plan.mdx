# How Design-Playground Works, End to End

<RichText id="mental-model" title="The Mental Model">

Design-playground is a **local-dev-only design canvas** that is _dropped into a host React + Vite app_ at `src/app/playground/`. It is never built in CI or production — it only runs inside the host's dev server. You drag components onto an infinite canvas (`@xyflow/react`), then use an agent CLI (Claude Code is the default and only visible provider) to generate AI layout and style variations, which render back onto the canvas as iterations.

Two design constraints shape everything: **zero dependency diff for the host** (the playground's deps install nested under its own `node_modules/`, and `react`/`vite`/`tailwindcss` are peerDependencies provided by the host) and **single embedded process** (the backend is a Hono app mounted into the host's Vite dev server via a plugin — there is no second server to run).

</RichText>

## The End-to-End Generation Loop

<RichText id="loop-intro" title="From Dropped Component to AI Iteration">

The core value is the generation loop. A component dropped onto the canvas becomes a node; the user asks for variations through the docked chat; the server spawns the agent CLI as a child process; the agent writes iteration artifacts (HTML frames and/or `.tsx` files) to disk; the server streams progress back; and the canvas renders each iteration as a new node. State is single-player and lives in `zustand` stores.

</RichText>

<Callout id="constraints" title="The Two Constraints That Explain the Odd Choices" tone="decision">

If a design decision looks unusual, it traces back to one of these: (1) **Zero host config diff** — no root `tsconfig`, peerDependencies for react/vite/tailwind, nested `node_modules`, imports stay relative (no `@` alias), and there is no shadcn `components.json`. (2) **One embedded process** — the Hono app must only answer paths it owns (`/playground/api/*`) and `next()` everything else, or it would 404 the host's own pages. `@hono/node-server`'s `getRequestListener` is mandatory for this bridge regardless of runtime.

</Callout>
