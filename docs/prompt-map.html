0 The 30-second mental model

One idea that makes every file in prompts/ click into place.

The playground is a prompt factory with a canvas bolted on top. A user gesture — drag, chat, Alt-click, an Adopt button — is compiled into a block of plain text, streamed to the claude CLI over stdin, and the agent responds by writing real files into your repo. The canvas then discovers those files and renders them.

In plain words

There is no clever runtime. Each feature is “assemble the right paragraph, hand it to the agent, watch the folder it was told to write to.” If you understand the paragraphs, you understand the product.

Four nouns, up front

A node is anything sitting on the canvas. The registry (registry.tsx) is the list of your real, imported components the canvas can render. An iteration is an AI-written variation — a new numbered .tsx file on disk. A skill is a markdown style-brief (SKILL.md) pasted into the prompt to steer the aesthetic. The chat box has three verbs: Explore (write new iterations), Edit (rewrite the selected file in place), Adopt (merge an iteration back into the original). Full glossary at the end.

Two facts fall out of this, and they explain almost every other design choice:

  • The prompt is the contract. The agent only knows what the text tells it — where to save, what to keep identical, how to style. Change the wording and you change the app's behaviour.
  • Two invariants are hard-coded into every generation prompt — a save path and a registration ritual. §5 shows how the SSE stream, the file-watcher, the index regeneration, and the EDIT_COMPLETE refresh are all just machinery serving those two sentences.

1 Two phases, one CLI

Prompts split cleanly into “understand the codebase” and “generate variations.”

A

Understand the host codebase

Three prompts read your app and write structured facts to disk — which files are components, their props, your design tokens. Cheap, read-mostly, run occasionally.

B

Generate variations

Nine generation prompts turn a selected node + your instructions into new files on the canvas. This is the loop you run all day. Every one funnels through a single endpoint.

2 Phase A — the “understanding” prompts

Three prompts that convert your repo into facts the generation prompts later depend on.

① Discovery scan → discovery.json

Scans every .tsx in the host repo and sorts each file into INCLUDE (renders real UI — a page or component worth showing) or SKIP (utilities, tests, config). It's told to decide cheaply: judge by path and filename first, open a file for a ~40-line peek only when ambiguous. The result is one JSON menu that becomes the sidebar tree.

features/generation/prompts/discovery.prompt.ts 
# classify from the path, open a file only when unsure
rg --files -g '*.tsx' -g '!node_modules' -g '!{playgroundDir}/**'
→ writes {playgroundDir}/discovery.json  (entries[]: id, name, path,
  type, description, status:"discovered", childComponents[])

② Analyze → the propsInterface

The deeper, per-component pass triggered on Add. It reads the component's source, extracts its real TypeScript props interface, and stores it on the registry entry. That interface text is what every Phase-B template later pastes in under “Props interface (DO NOT MODIFY)” — the two phases are joined right here.

features/generation/prompts/discovery-analyze.prompt.ts

③ DESIGN.md generation → design tokens

Reads the host's globals.css + tailwind config + component source and writes a DESIGN.md token spec in the @google/design.md format. Heavily fenced against fabrication: host app only, every token must trace to a real value, omit a section rather than invent one.

server/routes/design.ts → buildGenerateFromCodebasePrompt()
Note

This is the flow behind the “generate DESIGN.md from codebase” button. The prompt is the payload; the design.md CLI (runDesignMdCli) only lints the result afterward.

3 Phase B — the generation grid

Nine prompts across eight files. They vary on three axes plus two “special verbs” — once you see the axes, the list stops looking random.

Every generation template answers the same three questions differently:

  • Source — start from the original component, or from an existing iteration (the …FromIteration variants, which continue the numbering and lineage).
  • Scope — reshape the whole component, edit only Alt-selected elements (“copy verbatim, surgical edits only”), or invent a brand-new component from references.
  • Render mode — React means a normal registry component: it uses the host's Tailwind theme tokens and is saved to iterations/. JSX means a fully self-contained file: inline styles only, nothing imported except react, saved to canvas-components/. (Yes, both are technically JSX — “JSX” here is the playground's label for the portable, dependency-free kind.)
Worked example

You Alt-click two buttons inside an iteration node and hit Generate. Source = an iteration, scope = selected elements, mode = React → the app reaches for elementIterationFromIterationPrompt. Every row below is just a different answer to those same three questions.

Decode the names

Six of the nine rows are one family, and the name is assembled straight from the axes: an optional scope prefix (element = only the selected elements, jsx = self-contained canvas file) + iteration + an optional FromIteration suffix (source is an existing iteration, not the original). The other three — freeformReference, edit, adopt — don't fit the grid; they're the special verbs.

Nine rows, eight files — the two element rows are one template file with a source switch.

● The “iterate” verbs — additive

The six iteration templates all write new numbered files and never touch the source. Each ends with the same sequential ritual so files pop onto the canvas one at a time.

◑ The two “mutate” verbs — in place

Edit rewrites the selected file with no new node — and no new file means no file-watcher signal, so an explicit EDIT_COMPLETE event tells the canvas to refresh. Adopt rewrites the original to take an iteration's UI while keeping props/API byte-identical.

The element-targeted trick

Element iterations don't “redesign.” Their prompt says copy the file verbatim, then surgically change only the targeted elements — everything else must stay pixel-identical. That instruction is the whole feature; the Alt-click selection just fills in which elements.

4 Shared building blocks

The templates are mostly the same paragraphs. shared-sections.ts is the parts bin they draw from.

Assembly happens client-side the moment you hit Generate: a fill function in registry.tsx takes the node + your instructions and slots them into a template. The result is one long string — the slots below. A generation prompt is that fixed skeleton plus optional injected sections. Anatomy of a typical iterationPrompt:

Prompt anatomy — slots filled per request
skillSectionshared formatter · the selected SKILL.md context, or the default skill when the box is empty
componentName · sourcePathfrom the registry entry — where the agent reads the original
propsInterfacefrom Phase-A analyze — pasted under “DO NOT MODIFY”
referenceNodesSectionshared formatter · other canvas nodes / images / text notes selected as design references
customInstructionsSectionshared formatter · the user's typed instructions (or a default)
iterationSavesBlockthe hardcoded Save as src/app/playground/iterations/… lines — one per file (see §5)
stylingConstraintshared resolver · picks the styling rules — host Tailwind tokens by default, or inline CSS when the active skill asks for unconstrained exploration
qualityChecklistshared resolver · the “props unchanged / registered / tree updated” checkboxes

The styling switch is worth calling out because it changes the visual result completely:

● tailwind (default)

“Use only existing Tailwind classes; prefer semantic theme tokens (bg-background, text-foreground…); no hardcoded hex; no inline styles.” Result inherits the host theme, incl. light/dark.

● inline-css

“Use inline style={{}} for any property; no Tailwind utilities.” Maximum creative freedom, no theme coupling — used by the unbounded-explore skill.

⚠ A quiet smell

The “sequential a–e” registration block is still re-inlined by hand in each template (~6 copies with tiny drifts) rather than shared. Deduplicating it into one constant is deliberate future work — kept out of the minimalism pass to keep that diff removal-only.

5 The two invariants that shape the whole app

This is the payoff. Nearly every non-prompt subsystem exists to serve one of these two sentences.

Invariant 1 — the save path

Every generation template hardcodes the same destination string:

Save as src/app/playground/iterations/{PascalName}.iteration-{N}.tsx

That literal src/app/playground/… prefix is baked into all eight templates and the JSX ones — and because a host might mount the playground elsewhere, generate.ts carries a compensating rewrite:

// server/routes/generate.ts — patch the prompt at runtime
if (playgroundRelativeDir !== 'src/app/playground')
  prompt = prompt.split('src/app/playground/').join(playgroundRelativeDir + '/');
Why this is candidate #1 (PlaygroundPaths)

The prompts are the single biggest consumer of the hardcoded root. “Delete the rewrite, one module owns the paths” isn't abstract cleanup — it's untangling a string that's copy-pasted across a dozen templates and then string-replaced at runtime. That's the whole bug class.

Invariant 2 — the registration ritual

Immediately after writing each file, every template orders the same sequence:

Process iterations ONE AT A TIME. For each:
  a. save the iteration file
  b. add the @iteration / @parent / @description metadata comment
  c. register it in iterations/index.ts   (map key MUST include ".tsx")
  d. add a matching entry to iterations/tree.json
  e. only then start the next one
→ "so each iteration is visible on the canvas as soon as it's done"

That one-at-a-time requirement is why four subsystems exist: the SSE tool-event stream (parse the agent's “I wrote file X” to reveal each iteration live), server-side index regeneration, the skeleton → iteration swap on the canvas, and the fs-watcher as a fallback for files written via shell. The EDIT_COMPLETE refresh (§3) is the edit-verb corner of the same story.

✓ The lens

When a subsystem looks over-engineered, ask which prompt sentence it's serving. Almost always it's one of these two. Simplify the sentence and the machinery downstream can shrink with it.

6 Two refactors this map points at

The two invariants from §5, seen from the refactoring side. (An ongoing architecture review numbers these #1 “PlaygroundPaths” and #6 “PromptBuilder”.)

● The templates are already clean

The eight *.prompt.ts files are well-isolated, documented, and single-purpose. They do not need to move. The parts bin (shared-sections.ts) is healthy too.

◑ The orchestration is the mess

registry.tsx owns the fill layer: generateIterationPrompt() & friends take 8 positional args, build the save-block strings, and hardcode the path. #6 PromptBuilder should move that assembly into features/generation behind a plain-data options object (no React, no positional args). The templates themselves stay put.

  • #1 PlaygroundPaths is foundational precisely because the prompts are the path's heaviest consumer (Invariant 1). Fixing paths makes the #6 extraction honest.
  • #6 IterationPromptBuilder is narrower than it sounds: move the positional-arg fill functions out of the React host registry into features/generation, and fold the ~8 duplicated “sequential a–e” blocks into the shared constants that already exist for them.
  • Everything else — the events, watcher, SSE — traces to Invariant 2. Any simplification there should start by asking whether the prompt could carry the signal more directly (it already does, via the tool-event stream).
Bottom line

The prompts are small, readable, and stable. The debt isn't in what we ask the agent — it's in the hardcoded path threaded through everything, and the registry moonlighting as a prompt assembler. Fix those two and the map stays this legible.

✦ Glossary

The prompt families and the nouns around them.

Phase A / “understanding” prompts
Discovery, Analyze, DESIGN.md — read the host repo and write facts (discovery.json, props interfaces, design tokens) that Phase B later consumes.
Phase B / generation templates
The eight *.prompt.ts under features/generation/prompts/ (+ JSX ones in shared/lib/prompts/) that turn a selection into new files via /api/generate.
Iterate vs Edit vs Adopt
Iterate writes new numbered files (additive). Edit rewrites the selected file in place. Adopt merges an iteration's UI back into the original, preserving its API.
…FromIteration variant
A template whose source is an existing iteration rather than the original component — continues the numbering and records @sourceIteration.
Render mode React / JSX
React = a registry component styled with the host's Tailwind tokens, written to iterations/. JSX = a self-contained canvas-component that may import only react, inline styles, written to canvas-components/.
Shared sections shared-sections.ts
The parts bin: styling constraint, quality checklist, props constraint, file-registration, and the formatters (children / instructions / skill / references / elements) injected into templates.
The two invariants
See §5 — the hardcoded save path and the register-in-index+tree ritual.
