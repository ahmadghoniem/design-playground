0 The 30-second mental model

One idea that makes every directory click into place.

The playground is a prompt factory with a canvas bolted on top. A user gesture — a drag from the sidebar, a chat message, an Alt-click, an Adopt button — is compiled into a block of plain text, streamed to the claude CLI over stdin, and the agent responds by writing real .tsx files into your repo. The canvas then discovers those files and renders them.

In plain words

There is no clever runtime. Every feature is “assemble the right paragraph, hand it to the agent, watch the folder it was told to write to.” If you understand the paragraphs, you understand the product.

Four nouns, up front

A node is anything on the canvas. The registry (registry.tsx) is the list of your real, imported host components the canvas can render. An iteration is an AI-written variation — a new numbered .tsx file on disk. A skill is a markdown style-brief whose path is pasted into the prompt to steer the aesthetic. The chat bar has two live verbs: Explore (write new iterations) and Edit (rewrite the selected file in place); Adopt is a third, on the iteration node.

Two facts fall out of this and explain almost every other design choice:

  • The prompt is the contract. The agent only knows what the text tells it — where to save, what to keep identical, how to style. Change the wording and you change the app's behaviour.
  • Two invariants sit in every generation prompt — a save path and a registration ritual. §5 shows how the SSE stream, the poll, and the index rebuild are all machinery serving those two sentences.

The path a single “make me 4 variations” request actually takes.

useChatSubmit picks the right template and calls the fill function in registry.tsx, which slots in the component's source path, props interface, skill paths, references and save-path lines.

3

POST /api/generate spawns the agent

One chokepoint for every verb. The server pipes the text to the claude CLI over stdin and reads back stream-json.

server/routes/generate.ts → shared/lib/providers/spawn-agent.ts
4

The client drops N placeholder nodes next to the parent so the canvas feels responsive while the agent works.

features/generation/useGenerationLifecycle.ts
5

The server parses tool_use/tool_result out of the agent's stream, rebuilds iterations/index.ts itself, and pushes an iteration-added SSE event. A 4s poll is the safety net.

server/lib/claude-jsonl.ts · GET /api/generate?action=events

Skeleton → iteration swap

useIterationScan diffs the server's file list against the canvas, creates real iteration nodes with edges back to the parent, and removes the skeletons.

The chat bar — the app's control surface

One component, features/chat/DockedChatBar.tsx, is where nearly all intent is expressed:

  • Explore — write N new iterations (count dragger, 1–4, default 3). Only shown in explore mode.
  • Edit — rewrite the selected file in place, no new node.
  • Freeform / raw — no frame selected: create a brand-new component from the prompt (skeleton lands on the canvas).
  • Model picker — click to cycle; skill picker — type /.
  • Pills — the edit target (blue), Alt-clicked elements (chips), reference nodes (green), images (purple).

Discovery — how host components get onto the canvas

POST /api/discover spawns the agent with the discovery prompt; the agent itself writes discovery.json (a menu of every INCLUDE/SKIP-classified .tsx). Pressing Add runs a second, deeper pass (/api/discover/analyze) that extracts the component's real TypeScript props interface and appends an entry to registry.tsx. That props text is what every generation template later pastes under “Props interface (DO NOT MODIFY)” — this is the seam joining discovery to generation.

Subtlety

The sidebar tree is built from registry.tsx, not from discovery.json. Discovery populates the modal; the registry is what the canvas can actually render.

Iterations — the lifecycle after the agent writes

  • Registration — iterations/index.ts (filename → component map) and tree.json (parent lineage). The server now regenerates the index from tool events.
  • Element selection — a penpal RPC bridge injects a child script into the iteration iframe; holding Alt enters select mode and hovering/clicking an element sends it back as a pill. This is what makes “change only this button” possible.
  • Adopt — merges an iteration's UI back into the original component while keeping its props/API byte-identical.
  • Delete — tree.json supports cascade or reparent.

Everything else

Header: project name label, preview theme cycle, Skills, Model settings, Clear, Refresh. Sidebar: the registry tree. Stores (zustand): model settings (persisted), preview color scheme, interactive-node. Images: base64 JSON upload → .playground/images/. project-id: scopes canvas state per host project and supplies the header project name.

Prompt anatomy

A generation prompt is a fixed skeleton plus injected sections. Assembly happens client-side in registry.tsx the moment you hit Generate:

Slots filled per request
skillSectionshared formatter · the paths of selected SKILL.md files (never their bodies — see §5)

qualityChecklistshared resolver · the “props unchanged / registered / tree updated” checkboxes

● tailwind (default)

“Use only existing Tailwind classes; prefer semantic theme tokens (bg-background, text-foreground…); no hardcoded hex; no inline styles.” Result inherits the host theme, incl. light/dark.

● inline-css

“Use inline style={{}} for any property; no Tailwind utilities.” Maximum creative freedom, no theme coupling. Triggered by exactly one skill id: no-bound-explore.

4 The two invariants

Nearly every non-prompt subsystem exists to serve one of these two sentences.

Invariant 1 — the save path fixed

Every generation template tells the agent where to write. This used to be a hardcoded src/app/playground/… string copy-pasted across every template, with a compensating string-replace in generate.ts for hosts that mounted the playground elsewhere. That's gone:

// one module owns the root; prompts call a helper
iterationsFile(`${PascalName}.iteration-${N}.tsx`)
// → "src/app/playground/iterations/…" or "app/playground/iterations/…"

shared/lib/playground-paths.ts resolves the root from disk on the server and, in the browser, fetches it once from /api/playground-root. The runtime rewrite is deleted.

Invariant 2 — the registration ritual

Immediately after writing each file, templates order this shared sequence (getSequentialIterationRitual in shared-sections.ts):

Process iterations ONE AT A TIME. For each:
  a. save the iteration file
  b. add the @iteration / @parent / @description metadata comment
  c. add a matching entry to iterations/tree.json
  d. only then start the next one

iterations/index.ts is rebuilt by the server from Write/Edit/MultiEdit tool events — agents must not hand-edit it. That one-at-a-time requirement is why the SSE tool-event stream and the skeleton→iteration swap exist: so each file appears the moment it lands rather than all at once at the end.

✓ The lens

When a subsystem looks over-engineered, ask which prompt sentence it serves. Almost always it's one of these two. Simplify the sentence and the machinery downstream shrinks with it.

5 Skills — and the impeccable skill

How the aesthetic gets steered, and the one entry that isn't like the others.

The big surprise: skills are injected by path, not by content

A selected skill does not get its markdown pasted into the prompt. Only its file path does. formatSkillSection wraps them in a header that says the quiet part out loud:

SKILL CONTEXT (read each SKILL.md at the repo paths below)
══════════════

skills/frontend-design/SKILL.md

The agent is expected to open those files itself. This is why the skills system is so small: it's a path registry, not a content pipeline.

Where skills come from

GET /api/skills — the only skills endpoint — scans two directories for any SKILL.md and merges them, with user skills shadowing builtins on id collision:

  • builtin — <playground>/skills/: design-variations, frontend-design, make-interfaces-feel-better, no-bound-explore, nothing-design, stick-to-design-system, ux-variation-designer.
  • user — <host>/.claude/skills/: whatever you installed with the external npx skills CLI.

Ids come from YAML frontmatter name or the parent directory name. skills/index.ts is a types-only module — there is no loader. If you pick no skill and type nothing, two defaults are injected: design-variations + frontend-design.

The impeccable skill

It is a synthetic client-side picker entry, not a skill on disk. IMPECCABLE_PARENT_ITEM is a hardcoded constant in shared/lib/impeccable-skill.ts that useImpeccableSkillPicker prepends to the API-derived list (and it filters out any real skill with the id impeccable first, so the synthetic entry always wins).

Where it lives in the UI: exactly one place — the / slash menu of the docked chat bar (DockedChatBar.tsx → ImpeccableSkillPicker). It is a two-level menu:

On submit it emits a 3-line pointer prompt

Not a style brief — an instruction to go read two files and apply a command flow to each iteration after writing it.

impeccablePromptFromSegment() 
IMPECCABLE SKILL
Read {root}/SKILL.md and {root}/reference/{command}.md.
After creating each iteration file, follow the "{command}" command flow from
those files and apply the result directly to the iteration file before

⚠ It currently points at nothing

{root} comes from the real skill's path if a skill with id impeccable is installed — otherwise it falls back to the literal skills/impeccable. No such directory exists in this repo, and it isn't in skills-lock.json. So today the emitted prompt tells the agent to read two files that aren't there. The design clearly anticipates installing it via npx skills add into .claude/skills/impeccable/, at which point the real path is picked up automatically — but as shipped, every impeccable command is a dangling pointer.

Two things impeccable is not

It has no relationship to styling mode — the tailwind→inline-css switch is triggered by exactly one id, no-bound-explore, and nothing else. And it isn't a “mode”: it's just another entry in the same picker that produces a differently-shaped prompt string.

⚠ The skills catalog is a UI without a backend

SkillsCatalogModal POSTs to /api/skills/add, /update, /remove and /preview. None of those four routes exist — skills.ts defines only the GET. Its FEATURED_SKILLS list is 8 hardcoded vercel-labs/agent-skills entries. skills-lock.json is written by the external npx skills CLI; the only reference to it in this codebase is a gitignore line.

6 DESIGN.md — removed

The DESIGN.md / design-system subsystem (modal, showcase canvas node, /api/design/*, pg-design-inject cookie prepend) has been deleted. Generation relies on the component source path, props interface, and host semantic Tailwind tokens directly.

Architecture debt (refactor, don't delete)

◑ constants.ts is a junk drawer

~500 lines mixing real constants (zoom, colors, timings) with 7 payload interfaces, runtime functions (getDisplayDimensions), event-name and storage-key registries, and server-only filesystem constants — all imported broadly by features and the server. Split it per-feature; types and functions don't belong here.

◑ registry.tsx moonlights as a prompt assembler

The fill functions take ~8 positional args, build the save-block strings, and live in the React host registry. Move the assembly into features/generation behind a plain-data options object — no React, no positional args. The templates themselves are clean and should stay put.

Bottom line

The prompts are small, readable and stable — the debt was never in what we ask the agent. It's in a constants junk drawer, a registry doing a second job, and a surprising amount of scaffolding for features that were never finished (skills install, error badges, screenshots, providers). Delete the dead half; refactor the two seams above; the map stays this legible.

✦ Glossary

The nouns, in one place.

Playground root
Where this package lives inside the host (src/app/playground or app/playground), resolved from disk by sentinel files. Owned by playground-paths.ts; never hardcoded.
Registry registry.tsx
The list of real host components the canvas can render, plus (today) the prompt fill functions.
Iteration
An AI-written variation: a numbered .tsx file under iterations/, listed in tree.json; index.ts is rebuilt server-side from those files.
Explore vs Edit vs Adopt
Explore writes new numbered files (additive, 1–4 at a time). Edit rewrites the selected file in place. Adopt merges an iteration's UI back into the original, preserving its API.
…FromIteration variant
A template whose source is an existing iteration rather than the original — continues numbering and records @sourceIteration.
Skill
A markdown style-brief. Only its path is injected; the agent reads the file itself.
Impeccable
A synthetic picker entry (not a file) offering 19 commands; emits a pointer prompt to a skill directory that isn't currently installed. See §5.
The two invariants
The save path and the sequential save → metadata → tree.json ritual. See §4.
