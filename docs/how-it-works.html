0 The 30-second mental model

Before any of the details make sense, hold this one idea in your head.

The Design Playground is not a separate app with its own copy of your components. It is a window that lives inside your real app’s dev server. It renders your actual components on an infinite canvas, and it uses an AI coding agent (the claude command-line tool) to write real files into your project when you ask for variations.

In plain words

Think of it as a sketchbook laid over your codebase. The agent is a junior designer who can read your files, take screenshots, and save new files — but everything it does ends up as ordinary code on disk, not magic hidden state.

Two ideas that will keep coming up:

  • The agent talks to your project through files. The playground writes a prompt, the claude CLI reads/writes files in your repo, and the playground watches for the results. There’s no database.
  • Two very different kinds of “thing” live on the canvas. (1) Real components imported straight from your app (styled by your app), and (2) self-contained iterations the AI generates from scratch (HTML or single-file React). Almost every confusing behaviour comes from mixing these two up.

2 Adding a page, from A to Z

What the ↻ Refresh button and the + Add button really do — including which prompt is sent to the AI.

There are actually two independent buttons people lump together. The ↻ Refresh icon just re-reads what’s already on disk. The + Add button is the one that calls the AI. Here is the full pipeline:

1

You click ↻ Refresh

This does not call the AI. It just re-fetches lists from disk: HTML pages and on-canvas JSX components. Cheap and instant.

GET /api/html-pages · GET /api/oncanvas-components
2

First time only: “Add my pages” → a discovery scan

The playground sends the claude CLI a prompt that says “list every .tsx that renders real UI, classify each as a page or component, and write the results to discovery.json.” The agent greps your repo and writes that one file.

POST /api/discover · prompts/discovery.prompt.ts → discovery.json
3

The sidebar tree appears

discovery.json is now a menu of everything the AI found — this is the “Header → 7 children” tree you’re seeing. Nothing has been added to the canvas yet; it’s just a catalogue.

discovery.json (entries[])
4

You click + Add on one component

This runs a second, smaller AI task called analyze. Its prompt says: figure out the safe component to import, invent realistic mock props for it, and wire it into the registry. (Full detail in the next section.)

POST /api/discover/analyze · prompts/discovery-analyze.prompt.ts
5

The agent writes two things

(a) a mock-data file at data/<Name>.mockData.ts, and (b) an import + entry in registry.tsx that points at your real component via the @/… alias.

data/<Name>.mockData.ts · registry.tsx
6

It shows up on the canvas — as the real component

Because registry.tsx literally imports your component, the canvas renders the actual code, fed the mock props. (This is also where the styling surprise comes from — see §6.)

Key correction

Adding a discovered component does not screenshot-and-recreate it. It imports the genuine component from your app and just makes up believable props. The screenshot step you noticed belongs to a different action — generating variations — covered in §4.

3 The component tree & its “traces”

Why “Header” shows a description and 7 nested children.

Everything in that tree is generated by the discovery scan (step 2 above) and stored in discovery.json. Each entry looks roughly like this:

{
  "id": "header",
  "name": "Header",
  "path": "src/components/layout/Header.tsx",
  "type": "component",
  "description": "A sticky top bar with a logo, nav links and a call-to-action.",
  "status": "discovered",
  "childComponents": [ /* Logo, NavLinks, … — 7 of them */ ]
}
  • The description is written by the AI during the scan — one sentence about what’s on screen, deliberately avoiding library names.
  • The 7 children come from childComponents. The scan notes them “for free” from the import lines it already saw in the file — it does not open every child. When you later Add the parent, the analyze step promotes those children into their own tree entries (that’s the code in discover.ts that pushes childEntries).
  • Status moves discovered → added once you add it, and a re-scan preserves anything already added.
In plain words

The tree is just a JSON file the AI filled in by skimming your repo. “7 children” means “this file imports 7 other UI components.” Nothing is rendered or generated until you press Add.

4 The screenshot step — what it’s really for

You saw a screenshot get taken and the AI “replicate” a component. Here’s the honest version.

◑ What it looks like

“When I add a component, it screenshots the real one and asks the AI to copy it — instead of just importing the JSX from my app.”

● What’s actually happening

The screenshot only happens when you generate variations (Iterate / drag-to-iterate) — not when you Add. And the real component is imported (§2). The screenshot is a visual reference, not a replacement.

When you ask for iterations, the playground:

  1. Takes a PNG of the node on the canvas (captureAndSaveScreenshot.ts, via html-to-image).
  2. Puts the image path into the iteration prompt as “here’s what it currently looks like — use it as visual reference.”
  3. Asks the agent to write brand-new, self-contained files — each variation is either a complete HTML document (inline CSS only) or a single-file React component whose only allowed import is react.

Why generate self-contained copies instead of reusing the import?

Because an iteration has to survive on its own:

  • It must render in isolation. HTML iterations live inside sandboxed <iframe>s; they can’t reach into your app’s CSS or providers.
  • It must be safe to write and run. Your real page might do server-only work (database calls, secrets). A from-scratch, dependency-free file can’t drag any of that onto the canvas.
  • It must be independently editable. Each variation is its own file you can tweak, adopt, or throw away without touching the original.

The screenshot exists precisely because the agent is writing a fresh file and can’t see your running component — it’s the AI’s eyes. Text-only models would otherwise be guessing at the layout.

So, to answer directly

Importing the JSX is exactly what Add does. The screenshot-and-recreate is a deliberate, different tool for making portable variations. Both are working as designed — they just serve different goals.

5 The empty folder & the mock-data files

Why canvas-components/ is always empty, and what data/*.mockData.ts is.

canvas-components/ — empty is normal

This folder is not where added components go. It holds only freeform on-canvas JSX — files named frame-1.tsx, frame-2.iteration-3.tsx, etc. — created when you generate a brand-new component directly on the canvas (not from a discovered/registry component, and not an HTML page).

If everything you’ve done is “add discovered components” and “create HTML pages,” this folder correctly stays empty except for its auto-generated index.ts. The three destinations, side by side:

REGISTRY
Added / discovered components →
registry.tsx + data/
HTML PAGES
Created pages & their variations →
public/<slug>/…/index.html
CANVAS JSX
Freeform on-canvas components →
canvas-components/frame-N.tsx

data/<Name>.mockData.ts — believable props

Your real components expect props (a footer needs links, a card needs numbers). On the canvas there’s no live app feeding them, so the analyze step writes a small file of realistic fake data and passes it in as props:

/* data/Card.mockData.ts — auto-written, safe to edit */
export const mockData = {
  className: 'max-w-md px-6',
  children: 'Your evaluation is on track. You have completed 6 of 10…',
};

It’s pure serialisable data — no imports, no functions. When the playground can reach your app’s real data source it will use a live snapshot (props-fetchers.server.ts); otherwise the AI invents plausible values. You can edit these files freely to change what the preview shows.

6 Why a newly added component loses its styling

The big one. Short answer: yes, it’s Tailwind — but not for the reason you’d guess.

Your added component is the real one, rendering the real class names like flex gap-4 rounded-lg shadow. The problem is that those class names were never turned into actual CSS on the /playground page.

In plain words

Tailwind doesn’t ship every possible class — it scans your files, sees which classes you use, and generates only those. If the page that renders your component was never scanned, the classes exist as text but have zero CSS behind them. The component shows up “naked.”

The exact chain in this project

  1. The /playground route is served by its own entry, dev-entry.tsx. That file imports only two stylesheets: playground-global.css and playground-tailwind-entry.css.
  2. playground-tailwind-entry.css scans only the playground’s own folder — @source "./**/*.tsx". It never scans your app’s src/components or src/features.
  3. Your host app’s Tailwind (src/index.css, loaded by main.tsx) does scan those folders — but that stylesheet is loaded on your app’s normal routes, not on the separate playground.html entry.
  4. Result: on /playground, the only Tailwind present covers playground files. A handful of design tokens (bg-background, text-foreground) are re-mapped by hand in the entry so they survive — which is why the component isn’t totally invisible — but the bulk of utilities (flex, grid, gap-*, p-*, rounded-*, shadow, text-sm…) produce nothing.
Why the code “looks” like it should work

A comment in the Tailwind entry assumes “the host’s global CSS is loaded on every route, including /playground.” That’s true for a Next.js host (a root layout wraps every route). Rewynd is a plain Vite host where /playground is a standalone HTML entry — so that assumption quietly fails, and host utilities never get compiled.

Two ways to fix it

● Load the host CSS (simplest)

Add one line to the host’s dev-entry.tsx:
import '../../index.css'
Now the host’s Tailwind (which already scans your components) is present on /playground.

● Widen the playground scan (portable)

Add host globs to playground-tailwind-entry.css:
@source "../../components";
@source "../../features";
so the playground’s own Tailwind compiles host utilities too.

Loading the host stylesheet is usually the cleaner choice: it guarantees the preview matches production exactly, including your theme tokens. Say the word and I can wire whichever you prefer.

7 The file-watcher, explained simply

What it is, why it existed, and why it’s now just a safety net.

When the agent generates variations, the new files appear on disk one by one — but the browser has no natural way to know the moment a file lands. The file-watcher was the original answer to “how does the canvas find out a new iteration was written?”

The old way — watch the folder

server/lib/generation-file-watcher.ts pointed Node’s fs.watch at the folders where iterations get written (the iterations dir, public/<page>/, the canvas dir). Whenever a matching file changed, it waited 500ms (to let a burst settle) and then poked the browser: “something changed, go re-scan.”

In plain words

Imagine watching a printer’s output tray and shouting “new page!” every time paper appears. It works, but you only know that something arrived — you have to walk over and read it to find out what.

That “go re-scan” signal carried no detail — not which file, not which iteration number. So the browser had to re-list everything and diff it. And because folder-watching can miss events, there was a second safety loop polling the server every few seconds. Two overlapping mechanisms, both guessing.

The new way — listen to the agent directly

The claude CLI already streams a structured play-by-play of what it’s doing, including “I just wrote file X.” The playground now reads that stream and forwards the exact file path and iteration number to the browser the instant it’s written. One authoritative signal, no folder-watching, no polling, no guessing.

✓ Where the watcher stands today

The tool-event stream is the primary mechanism. The old fs.watch code was demoted to a silent fallback — it only speaks up if no tool event was seen (e.g. the agent wrote a file via a raw shell command). Once we’re confident the stream covers every case, the watcher can be deleted entirely. It survives for now purely as a belt-and-braces backup.

The takeaway for AI-in-your-app generally

If your agent can tell you what it did in a structured stream, prefer that over watching the filesystem for side-effects. Watching the disk tells you something happened; listening to the agent tells you exactly what — with far less code and far fewer race conditions.

✦ Glossary

The nouns that fly around this codebase.

Discovery scan discovery.json
An AI pass that catalogues your repo’s UI files into a JSON menu. Powers the sidebar tree. Cheap, read-only.
Analyze / Add
Turning one catalogue entry into a live canvas component: writes mock data + a real import into registry.tsx.
Registry registry.tsx
The hand-and-AI-maintained list of real components the canvas can render, each paired with mock props.
Frame
Something you created in the playground (an HTML page or a canvas JSX component), as opposed to a discovered component.
Iteration
An AI-generated variation. Always a fresh, self-contained file (inline-CSS HTML, or single-file React that imports only react).
Mock data data/*.mockData.ts
Realistic fake props so a real component can render on the canvas with no live app behind it.
Tool-event stream
The structured “I wrote file X” messages from the claude CLI. Now the primary way the canvas learns what was generated.
File-watcher
The legacy folder-watching fallback that used to detect new files. Being retired in favour of the tool-event stream.
