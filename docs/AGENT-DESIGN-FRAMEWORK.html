Teaching agents product design: Vercel's method vs. our design-playground

A plain-language map of Vercel's "Teaching agents product design" onto this codebase — what it is, how it differs from how we already do things, where it fits, where it doesn't, and the few pieces actually worth stealing. Jargon is glossed inline in green the first time it appears.

Plain-language key

Six terms do most of the heavy lifting. Here they are in one place so the rest reads cleanly.

Converge / convergence
Narrowing many options down to the one right answer, and then making everyone stick to it. (Vercel's goal.)
Diverge / divergence
Fanning out into many deliberately different options so a human can compare and pick. (Our playground's goal.)
Skill
A markdown instruction file (SKILL.md) that teaches the AI a way of thinking — taste, rules, a design system. We already have seven of these.
Linter
An automated rule-checker that scans code and flags mechanical violations (e.g. "this radius is wrong"). It checks facts, not taste.
Reachable state
Every situation a UI can actually end up in: loading, empty, error, disabled, mobile-width — not just the one perfect "everything-loaded" screenshot.
Eval (with an LLM judge)
A test for AI output: run the prompt, then have a second AI score the result against a rubric. "Holdouts" are hidden test cases the AI hasn't seen, used to check it actually learned the rule instead of memorizing.

0The one idea that reframes everything

The reframe

Vercel built a convergence engine. We built a divergence engine. They are near-opposites — and that single fact explains every difference below.

  • Vercel's product-design skill exists to make every AI agent land on the one accepted decision ("destructive actions are labelled Verb + Noun", "never stack two modals") and apply it consistently across a real shipping product.
  • Our playground exists to do the opposite: produce four deliberately different takes on a component, lay them on a canvas, and let a solo builder choose. Our own skill says it outright — "Diverge first, converge later… expand the design space, not find the best version" (skills/design-variations/SKILL.md).

So you can't drop Vercel's framework in as-is — it would fight what the product is for. But several of its mechanisms plug straight into gaps we genuinely have. The rest of this doc keeps the parts that fit separate from the parts that don't.

2How our method actually works (grounded in the code)

Every generation is built from three layers.

a) Prompt builders — prompts/*.prompt.ts

One template per kind of job: iteration, iteration-from-iteration, element-iteration, jsx-iteration, edit, adopt, create-page, html-iteration, freeform-reference. Each assembles the same shape: an optional skill block → request details (component, path, how many, how deep) → instructions → hard requirements → a "be creative" block → a quality checklist.

b) The quality checklist — the only enforced gate

Defined in prompts/shared-sections.ts (getQualityChecklist). The catch: it is entirely mechanical i.e. it only checks the code compiles and is wired up — never whether the design is any good:

- [ ] Props interface unchanged from original
- [ ] All imports resolve, no TypeScript errors
- [ ] Metadata comment with @iteration / @parent
- [ ] File named PascalCase.iteration-{n}.tsx
- [ ] Entry added/updated in iterations/tree.json
- [ ] Styling mode honored (theme tokens vs inline CSS)

Every line answers "did it build and register?". Not one asks "is this a good product decision?" — that judgment is handed entirely to the model and to whichever skills the user switched on.

c) Skills — skills/<name>/SKILL.md

Injected into the prompt by formatSkillSection, but only when the user selects them. These carry all the actual design opinion:

d) Evals — evals/

A strong pattern, but narrow: it only tests discovery.prompt.ts (the scan that finds components), nothing about generation. It runs the real prompt through the real spawnAgent('claude-code'), then combines two checks:

  • Deterministic structural checks (structural-checks.ts) — machine-verifiable facts: kebab-case ids, that file paths exist on disk, skip-rule violations, a banned-words list for descriptions.
  • An LLM judge (judge.prompt.ts) — a second AI scores the output 1–5 across six dimensions and suggests concrete wording fixes, measured against a ground-truth file inventory.

It even recommends running the same prompt on haiku, sonnet, and opus to expose fragility a prompt that only works on the smartest model is under-specified. This is exactly Vercel's eval philosophy — just aimed at one prompt instead of the whole product.

3Vercel's framework, in plain terms

Three pillars, held together by a set of always-on principles.

The three pillars

  1. An agent skill (the judgment layer). Guidance that's looked up based on what you're working on "routed by surface": a modal pulls the modal rules, a settings form pulls the form rules — nothing is duplicated. It includes references/ (guidance per screen-type) and exemplars/ — saved real pull requests with the reasoning written down.
  2. Linters (the deterministic layer). Hard rules with stable names like rule/destructive-names-action, each explaining why plus a fix, some auto-applying. Their line: "Code can count two or three static options, so a linter can recommend radio buttons" — i.e. let machines handle the countable stuff.
  3. A review loop (the learning layer). Weekly, in three deliberately separate phases: collect evidence → group & sanity-check it → a human decides whether it becomes guidance, a lint rule, an example, an eval, or nothing. "Automation ends with the review packet. A human decides."

The always-on principles (their "operating contract")

Eight rules the agent never drops: start with the job, not the pixels · define the outcome before the output · use evidence, not taste · separate facts from decisions · treat shipped code as evidence, not automatic precedent · make the smallest coherent change · decide before decorating · design every reachable state. Plus: verify the rendered screen, not just the source code.

Request modes (scope guards)

Five categories that stop an agent from quietly doing more than asked — pick the narrowest one the verb supports: Shape (frame the problem, don't edit) · Implement (decide, then make the minimal change) · Review (report findings, don't edit) · Copy (wording only) · Harden (fix resilience / responsive / accessibility without changing the direction).

The phrasing most worth stealing

Prefer observable decisions over vague adjectives. "Destructive actions use Verb + Noun" can be checked; "Buttons should be clear" cannot. Their decision template is just: Decision / Rationale / Evidence / Exceptions / Good example / Bad example / Open decisions.

5The three real gaps (highest leverage first)

Gap 1 — we throw away the signal of which option won

When the builder drags iteration-3 off the canvas and keeps it, nothing records that choice or the reason for it. That pick is the single richest design signal in the whole app — and it evaporates. Vercel's entire review loop exists to capture precisely this.

Steal: an "Accept / Promote" action on an iteration node that writes a small decision file (docs/decisions/{component}-{n}.md) using Vercel's template — what changed, why this one won, a screenshot. Over time these become worked examples that get fed back into the iteration prompt ("here's what this builder has accepted before"), turning a forgetful tool into one that learns the builder's taste. Highest-value, most on-brand add.

Gap 2 — we never design the states that aren't the happy path

Every iteration prompt says "make variations" of the component as it is. None ask for the loading, empty, error, disabled, or mobile-width versions. "Design every reachable state" is the cheapest quality upgrade on the table.

Steal: a state axis (like the divergence axes in design-variations) or a dedicated Harden mode that, instead of restyling, fills in the missing reachable states of the selected component. Reuses all the existing spawn/iteration plumbing.

Gap 3 — our best linter is trapped in prose

make-interfaces-feel-better is really 16 machine-checkable rules (concentric radius, exactly scale(0.96), no transition: all, tabular numbers, 40×40px hit areas). Today they only apply if the user opts the skill in, and nothing verifies them after generation.

Steal: promote the checkable subset into actual post-generation checks — evals/structural-checks.ts already proves we can statically read generated .tsx. Run them over each new iterations/*.tsx and surface violations as badges on the canvas node. Keep the genuinely subjective rules ("spend your boldness in one place") as judgment in the skill. That split — facts to the checker, taste to the skill — is Vercel's lint/skill division.

6Where Vercel's framework does not fit

Don't force these

  • "Evidence not taste" / the decision-authority ranking. Vercel optimises toward consensus; we deliberately optimise toward surprise (our skill literally asks for "at least one direction that feels uncomfortable"). Importing this wholesale would neuter the divergence skills.
  • Guidance looked up per screen-type. That assumes a stable shipping product with recurring screens. The host app is that — but the playground is a lens over the host, not the owner of its design decisions. That routing belongs in the host.
  • The weekly human review meeting. We're single-player, local-dev, throwaway. The lightweight version (Gap 1's per-accept decision file) is the right size; a weekly review packet is not.
  • "Observable over adjectives" for the creative skills. There, adjectives are a feature — they widen the space. Keep them. Apply the "observable" discipline only to the quality gate, never the creative prompt.

7A phased way to try it

  1. Cheap & on-brand: add the state axis / Harden mode (Gap 2). Pure prompt work, reuses existing job kinds.
  2. The keystone: add Accept → decision file + saved example (Gap 1), then feed accepted examples back into iteration.prompt.ts via a new formatExemplarsSection. This is the convergence-memory the app completely lacks.
  3. Hardening: lift the checkable make-interfaces-feel-better rules into a lib/ static checker reusing the structural-checks.ts pattern; show violations as canvas badges (Gap 3).
  4. Confidence: extend the evals/ harness from discovery to generation — score a before→after of a component against a quality rubric, with holdouts to confirm a skill generalises instead of memorising.

The throughline: keep the divergence engine exactly as it is, and bolt on the convergence memory that Vercel's framework is fundamentally about — scaled down to a solo, local, throwaway tool.
