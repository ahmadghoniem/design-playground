# TailwindEditor (prabhatpushp/TailwindEditor) — research notes

TailwindEditor is a Next.js 16 / Tailwind v4 app: a Figma-shaped visual editor whose right-hand panel writes literal Tailwind utility classes onto a live HTML preview, backed by a Monaco code editor as the source of truth. It is the closest existing implementation of "controls that read/write Tailwind classes instead of CSS," which is why it's the most relevant of the three repos studied. ## 1. Architecture

Next.js App Router shell (`app/page.tsx` → `components/editor/desktop-editor.tsx`, 53 lines) composes three panes: a left sidebar (`left-panel.tsx`, blocks/layers/assets/pages), a center **iframe preview** (`iframe-panel.tsx`) or Monaco code editor (`code-editor-panel.tsx`, 452 lines), and the right **properties panel** (`properties-panel.tsx`, 46 lines, thin wrapper) which renders `design-panel.tsx`.

**The preview is a real `<iframe>`**, not an inline-DOM overlay. `iframe-panel.tsx` builds an HTML document (`srcdoc`/injected script, generated around line 23 onward) containing a hand-rolled selection/hover/drag runtime, and the two sides talk over `window.postMessage` with `source: 'iframe-builder'` (send: line 545 inside the injected script; receive: parent listener at line 2196–2252+). Class/text/id/style edits are pushed to the iframe via targeted `postMessage` calls (lines ~2077–2170) rather than full document reloads, to avoid flicker. This iframe boundary is structural — it's *why* their selection model, their DOM traversal, and their edit-application model can all assume they own literal `class="..."` strings on real DOM elements: the editor is editing text (raw HTML/JSX-looking source in Monaco), not a live React tree.

## 2. Mechanisms we might copy

### `lib/tailwind-conflict-groups.ts` — the property→regex registry

`CONFLICT_GROUPS: Record<string, RegExp>` (line 37) maps ~140 keys (`position`, `fontWeight`, `textColor`, `borderRadius`, `ringWidth`, `translateX`, …) each to one anchored regex matching every valid Tailwind utility for that property, base-form only (no breakpoint/pseudo prefix — those are stripped first).

- **Colors** are handled by a shared helper, `colorPattern()` (line 31), built from two constants: `TW_COLORS` (the 22 Tailwind scale names, no shades) and `TW_COLOR_KEYWORDS` (`inherit|current|transparent|black|white`). It produces `(keyword | scaleName(-\d+)?(\/[\d.]+)?  | \[...\])`, i.e. it matches `red-500`, `red-500/50`, `transparent`, and any `[...]` arbitrary value starting with `#` or a letter — but it has **no concept of a design-token name** (`bg-primary`, `text-brand-fg`) unless that exact string collides with one of the hard-coded scale names. A token class like `text-brand` would simply fail to match `textColor`'s negative-lookahead exclusion list and get treated as "other"/unrecognized in the simpler `tailwind-utils.ts` parser, or in the conflict-group world, silently *not* be removed when the property is later changed (see `replaceConflictingClasses` below) — because the regex for `textColor` (line 337) is a negative-lookahead constructed from a hardcoded keyword blacklist, not an allowlist, so it *would* actually match `brand` too (anything not in the blacklist and not starting with a digit). In short: token color classes accidentally work by falling into the catch-all negative-lookahead pattern, not by design.
- **Arbitrary values** are matched generically via `\[.+\]` (or a more specific `\[[#a-zA-Z][^\]]*\]` inside `colorPattern()`), so `w-[500px]`, `translate-x-[10px]`, and even v4-style bracket properties like `[transform:rotateX(45deg)]` (used for the 3D-transform section, see line 617–629) all round-trip through the same registry.
- **Extension** is manual: add a new `key: RegExp` entry, then reference that key from the design panel when calling `updateClasses`. There is no code generation from a Tailwind theme/config; every entry is hand-authored against Tailwind's *static* vocabulary.
- **Consumption**: the single public entry point is `replaceConflictingClasses(currentClasses, conflictGroupKeys, newClass, activeBreakpoint)` (line 797). It splits the class string on whitespace, and for each requested conflict-group key calls `removeMatchingClasses` (line 748), which strips a class only if (a) its modifier chain exactly equals the active editing context (`""` for base, or e.g. `"md:"`) and (b) its base utility matches the group's regex — then appends the new class (breakpoint-prefixed). `extractModifierAndBase` (line 714) is a small bracket-depth-aware colon scanner so that arbitrary values containing colons (`text-[color:red]`) aren't mis-split. This is the mechanism actually wired into `design-panel.tsx` (`updateClasses` at line 225) — every control on the panel calls it with one or more conflict-group keys.

### `lib/tailwind-utils.ts` — `parseClasses` / `buildClasses` / `updateClass` / `replaceClassPattern`

This is a **second, independent** implementation of the same idea, and it appears to predate/parallel the conflict-groups system rather than being layered on top of it — `design-panel.tsx` only imports `parseClasses` from it (for read-side display: computing `justifyContent`, `alignItems`, etc. to drive `active` states on buttons) and imports `replaceConflictingClasses` from the *other* module for all writes. `buildClasses`/`updateClass`/`replaceClassPattern` are exported but not used by the panel.

- `parseClasses(className, breakpoint)` (line 60) walks the class list once, and for each class either (a) buckets it into a **fixed, hand-enumerated set of named fields** on a `ParsedClasses` object (`display`, `flexDirection`, `padding.{t,r,b,l,all}`, `fontSize` vs `textColor` disambiguated by whether the text-suffix is a known size token or starts with `[`, etc.) or (b) if nothing matches, pushes the raw string into `other: string[]`. Filtering by breakpoint: any class whose own `breakpoint:` prefix doesn't equal the requested one is shoved into `other` unconditionally — i.e. this parser can only ever look at *one* breakpoint's classes at a time and treats every other breakpoint's classes as inert passthrough content it must not disturb.
- `buildClasses(parsed, breakpoint)` (line 329) is the literal inverse: it re-serializes each recognized field back to `prefix + 'property-' + value` in a fixed order, then appends `other` classes at the end. **What's lost in the round-trip**: original class *ordering* within the recognized set (everything gets re-emitted in the function's hardcoded field order, not the source order), and any information about *why* a class ended up in `other` (arbitrary Tailwind features this parser doesn't know about — e.g. `divide-*`, `ring-*`, `backdrop-*`, container queries, `has-*` — pass through unexamined as opaque strings). It is also lossy in a subtler way: `parsed.padding.l`/`.r` both get set from `px-*`, but `buildClasses` only re-emits them as independent `pl-`/`pr-`, so a round-tripped `px-4` becomes `pl-4 pr-4` unless `padding.all` happens to be set — an asymmetry between parse and build for the x/y shorthand.
- `updateClass(currentClasses, property, value, breakpoint)` (line 481) is a convenience wrapper: parse at `breakpoint=''` (always base — this ignores the `breakpoint` arg on the *read* side, a latent bug if ever called with a non-base breakpoint), mutate one field (supports dotted paths like `padding.t`), then `buildClasses(parsed, breakpoint)`.
- `replaceClassPattern(currentClasses, pattern, newClass)` (line 544) is the simplest of the four: split, filter out anything matching an arbitrary `RegExp`, push the new class. No breakpoint awareness at all — this is essentially what `CONFLICT_GROUPS` + `removeMatchingClasses` supersede with breakpoint/modifier scoping.
- **`BREAKPOINTS`** (line 6): `['', 'sm:', 'md:', 'lg:', 'xl:', '2xl:']` — a fixed array driving the panel's device-switcher; the empty string represents "base/no breakpoint." Editing at a given breakpoint means every write goes through `parseClasses(_, breakpoint)`/`replaceConflictingClasses(_, _, _, activeBreakpoint)`, which is what keeps `sm:` and `md:` variants from clobbering each other or the base — but note this is a flat mobile-first breakpoint list with no concept of container queries, dark-mode (`dark:`) or state (`hover:`) as an *orthogonal* axis to combine with breakpoints; the modifier-chain scanner (`extractModifierAndBase`) treats the whole prefix chain as one opaque string keyed by exact match, so editing "hover at md" as a distinct target isn't a first-class concept in the UI, only in the low-level string matching.

### Panel primitives — measurements

- **`PropertyRow`** (`property-row.tsx`, 17 lines): a flex row, fixed height **`h-7` (28px)**, label in `text-[10px] text-muted-foreground font-medium` on the left, control column pinned to `w-[120px]` and right-aligned on the right. This two-column fixed-width-label / fixed-width-control layout is what makes the long panel scannable — every row's control starts at the same x-offset regardless of label length.
- **`PropertySection`** (`property-section.tsx`, 44 lines): header row `px-4 py-3`, title `text-xs font-medium`, a `ChevronDown` (`w-3.5 h-3.5`) that rotates 180° on open, animated via CSS grid-template-rows (`grid-rows-[1fr]`/`[0fr]`, 300ms) rather than height/opacity — avoids measuring scrollHeight. Body padding when open: `px-4 pb-4 pt-1`. Border-bottom `border-border/50` separates stacked sections; no visual card/shadow — sections read as one continuous scroll.
- **`PropertySelect`** (`property-select.tsx`, 338 lines): trigger button `h-7`, default `w-[120px]` (i.e. matches `PropertyRow`'s control column exactly), text `text-[10px]`. Popover content fixed `w-[224px]`, max-height `340px`. Has an inline unit-picker (`w-14` button) that only shows for numeric-style properties (`hideUnits` prop suppresses it for keyword-only pickers like `display`).
- **`SizingInput`** (`sizing-input.tsx`, 406 lines): label above (not beside) the control, `text-[11px]`; control itself `h-8`, `text-xs font-mono`. This one is notably **not** class-shaped: it stores/returns raw CSS-style values (`"1rem"`, `"50%"`, `"100vh"`) via a portal-rendered popup of hand-curated presets (Containers/Relative/Viewport/Content/Spacing Scale categories with `{label, value, desc}` triples, e.g. `{label:"md", value:"28rem", desc:"448px"}`). The design panel's callers then do the class-string conversion themselves at the call site (`onChange={(val) => updateClasses("width", val ? \`w-${val}\` : "")}\` — design-panel.tsx line 547), i.e. `SizingInput` emits a CSS length and the caller re-wraps it as `w-${val}`. This is an inconsistency worth noting: two of their five "primitives" (`PropertySelect`'s custom-value path and `SizingInput`) work in raw CSS-value space and rely on the consuming call site to Tailwind-ify the result, while the conflict-groups system downstream expects a bare utility suffix, not a full class or a raw value — the seam between "value editor" and "class writer" isn't type-enforced, it's a per-call-site convention.
- **`ColorPicker`** (`color-picker.tsx`, 1572 lines): full Tailwind palette rendered as `grid-cols-10` swatch grids (10 shades × N hue rows) sourced from a hardcoded `TAILWIND_COLORS: Record<string, string>` hex map (line 38) plus a reverse `HEX_TO_TAILWIND` lookup (line 369) used to snap arbitrary hex back to a named Tailwind color when possible. Popover is `w-[280px]`/`h-[360px]` (simple picker) or `w-[340px]`/`h-[480px]` (the tabbed advanced picker with a 4-tab `TabsList`, gradient stops, HSL sliders). No notion of a project's theme tokens — every swatch is a literal `red-500`-style Tailwind scale color.

### `design-panel.tsx` — section list and commit path

Ten `PropertySection`s in this exact order: **Element** (text/className/style/id raw textareas — the escape hatch), **Alignment**, **Sizing**, **Layout** (position/display/grid-or-flex sub-controls/margin/padding), **Styles** (opacity/blend-mode/cursor), **Typography**, **Borders** (width/color/radius/ring), **Effects** (shadow/blur/backdrop-blur/brightness/contrast/saturate/hue-rotate/grayscale/invert/sepia), **Transforms** (translate/rotate/scale/skew/origin), **3D Transforms** (rotateX/Y/Z, perspective, transform-style, backface-visibility — all emitted as raw `[transform:rotateX(45deg)]`-style arbitrary-value classes rather than named utilities, since Tailwind has no built-in 3D-transform utility set).

Every control funnels through one of two `useCallback`s defined at the top of the component (lines 225–335):
1. `updateClasses(conflictGroup, newValue)` (line 225) — the general path. Resolves the elements to update (multi-select aware: `selectedElements` if non-empty, else `[selectedElement]`), and for each calls `replaceConflictingClasses(element.className, conflictGroup, newValue, activeBreakpoint)`, then `updateElementClasses(element.builderId, newClasses)` from the zustand store. Batch/multi-select editing is handled simply by looping and applying the same operation to every selected element's independent class string — there's no diffing or "mixed value" indicator in the read side beyond what `parsedClasses` (computed once, from `selectedElement` only) happens to show.
2. `updateBackgroundClasses(newValue)` (line 241) — a special-cased variant for backgrounds because a single logical "background" edit can expand to multiple classes (`bg-gradient-to-r from-red-500 to-blue-500`) that need per-part breakpoint-prefixing and can't be expressed as one conflict-group replacement; it hand-parses/reconstructs with its own filter predicate (excluding `bg-opacity-`, `bg-blend-`, `bg-clip-`, position/repeat/size keywords, etc. from being swept up as "old background classes") since `CONFLICT_GROUPS.backgroundColor` alone wouldn't know to also strip stale `from-`/`via-`/`to-` gradient stops.

`parsedClasses` (line 214, a `useMemo` over `selectedElement.className` + `activeBreakpoint`) is the panel's only read source, computed via `parseClasses` from `tailwind-utils.ts` (not the conflict-groups module) — so *reading current state* and *writing new state* go through two different parsers/serializers that happen to agree on utility prefixes but are otherwise unrelated code paths.

### Selection tracking and how a change reaches the source

`lib/store.ts` (zustand, 517 lines) is the single source of truth: `code: string` (the full HTML/JSX-looking document as Monaco sees it), `elementPositions: Map<string, ElementPosition>` (line-column spans per `builderId`, produced by `injectBuilderIds` in `lib/html-utils.ts`), and `selectedElement`/`selectedElements` (plain JS objects carrying `builderId`, `className`, `style`, `id`, `innerText`, `tagName` — a snapshot, not a DOM reference).

`html-utils.ts`'s `injectBuilderIds` (line 7) is a **hand-rolled, non-AST HTML tag scanner** (find `<`, find matching `>`, extract tag name, skip `script/style/link/meta/title/head/html/!doctype`, find the matching close tag by depth-counting) that stamps `data-builder-id="__bid_N"` onto every element's opening tag and records its line/column span. This is how the iframe's runtime script can report "user clicked element N" back to the parent purely by DOM attribute, while `store.ts` can locate that same element in the *text* of `code` purely by string search — the two representations (rendered DOM vs. source text) are kept in sync only by this shared, deterministically-ordered ID, never by AST node identity.

The write path (`updateElementClasses`, `store.ts` line 186) is a **pure string operation**: `updateClassInHtml(code, builderId, newClasses)` (line 322) builds a regex `<[a-zA-Z][a-zA-Z0-9]*[^>]*data-builder-id="ID"[^>]*>` to find the element's full opening tag as one regex match, sniffs `isJsx` by checking whether the tag already has `className=` or the whole document contains the literal substrings `"React"`/`"jsx"` (line 334 — a heuristic, not a parse), picks `class` vs `className` accordingly, and then either replaces an existing `class(Name)="..."` attribute value via a second regex or splices a brand-new attribute in right after the tag name. There is no AST, no diffing, no `prettier`/formatter pass — the Monaco buffer is regenerated as a full string and pushed back into the editor (and separately, a *targeted* `postMessage` patches just that element's `class` in the live iframe DOM so the preview doesn't need a full reload/flash).

### What survives the HTML-vs-React difference, and what doesn't

Their whole write pipeline assumes **the selected node's class attribute is one literal, regex-locatable string** in the source text, addressed by a single injected marker attribute. That assumption survives cleanly for us only in the narrowest case: a JSX element whose `className` prop is a bare string literal (`className="flex gap-2"`) with no host-app minification/formatting in between edits — conceptually the same operation `replaceConflictingClasses` performs (remove classes matching a conflict-group regex within the correct breakpoint/modifier scope, append the new class) is representation-agnostic and **is** directly reusable as a pure string→string function once we've already extracted the class string.

What does not survive is everything upstream of that string: their `data-builder-id` + regex-tag-match location strategy assumes the "source" and the "rendered output" are the *same literal text* (HTML editing HTML). Our source is a `.tsx` file compiled/transformed before it renders, and — per our constraints — a shadcn/Radix component's actual class string is frequently the *return value of `cn(buttonVariants({variant,size}), props.className)`*, not a string literal anywhere in the file the developer will save. There is no `class="..."` attribute in the source for `injectBuilderIds`-style regex to find, no single literal for `updateClassInHtml`-style regex to replace, and no guarantee the rendered DOM's `className` (post-`cn()`, post-`tailwind-merge`) has any textual relationship to what's written in JSX at all — it may be entirely synthesized from `variant`/`size` props rather than a string. Their `isJsx` heuristic (checking for the substring `"React"` anywhere in the file) is also not something we can lean on; we already know statically we're in JSX everywhere. The upshot: we can reuse the *conflict-group regex registry and the remove-then-append algorithm* verbatim as a class-string transformer, but we cannot reuse their *element→source-location* strategy at all — we need our own mechanism (e.g. resolving back to a `props.className`/prop argument in the AST, or to a `variant`/`size` prop when the class is variant-generated rather than literal) since a DOM-attribute regex has nothing to find in the `cn(buttonVariants(...))` case.

## 3. What they do that we deliberately won't, and why

| Their choice | Why it's wrong for us |
|---|---|
| **Row labels in CSS-property vocabulary implicitly** (their UI groups by "Sizing"/"Layout" and reads back via `parseClasses`'s fixed field names like `fontSize`, `lineHeight`) rather than surfacing the Tailwind utility name itself as the label | We were told rows must be labeled in Tailwind's own vocabulary (`tracking`, `leading`, `ring`, `space-y`) — their panel labels things generically ("Line Height", "Letter Spacing") and only the *value picker* speaks Tailwind (`leading-tight`). For us the label itself is the utility family name, which also disambiguates ambiguous prefixes (`text-` as size vs. color vs. align) in a way their fixed-field parser handles by ad hoc heuristic (line 229's regex check for alignment keywords before falling through to size-vs-color) rather than by an explicit, told-to-the-user distinction. |
| **Full raw-hex Tailwind palette color picker with no token awareness** (`TAILWIND_COLORS` hardcoded hex map, `grid-cols-10` swatches, `HEX_TO_TAILWIND` snap-back) | Wrong for a host app using `@theme inline` semantic tokens: the picker needs to *lead* with the host's own token names (and be able to tell which are actually defined vs. mapped-but-dead in the CSS layer) rather than a generic `red-500`/`blue-600` scale that has no relationship to the design system the developer is actually shipping. Offering the full raw scale as primary UI encourages exactly the un-reviewable, off-system color literal a token-aware panel exists to prevent. |
| **9 (really 10) sections including full 3D Transforms** (perspective, `rotateX/Y/Z`, `transform-style`, `backface-visibility`, all emitted as raw `[transform:rotateX(...)]` arbitrary-value classes since Tailwind has no native 3D-transform utilities) | This is optimizing panel completeness for a general-purpose site builder. A component-library-scoped, developer-review-facing panel doesn't need CSS-3D controls that don't correspond to any real Tailwind utility class in the first place — every row in that section writes an arbitrary-value escape hatch, which is precisely the kind of output a developer reviewing the diff would flag as unusual/unmaintainable, not a normal use of the class system the rest of the panel is built to speak. |
| **Iframe preview** as the whole basis for selection + live edit application | Explicitly ruled out by our architecture — `design-playground` renders previews inline in the same document (plain DOM selection via Alt+hover, `useElementSelection.ts`/`extractElementContext`), specifically because there's no iframe RPC bridge (`penpal` was removed). Their entire selection/edit-application design (injected script, `postMessage` protocol, `data-builder-id` DOM stamping synced to source-text line/column spans) is a direct consequence of the iframe boundary; adopting any piece of it (the marker-attribute + regex-tag-locate strategy in particular) would be re-introducing the iframe's problem (text ⇄ DOM address translation) into a codebase that deliberately doesn't have that problem, since our selected element already *is* a real node in the same-document React tree, addressable without any marker-and-regex indirection. |
