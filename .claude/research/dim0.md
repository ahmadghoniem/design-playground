# Dim0 (`vcmf/dim0`) — research notes

Dim0 ("The Thinking Canvas") is an open-source (MIT), cloud-hosted infinite canvas: notes, mini-apps, code sandboxes, and documents as nodes on a real-time-multiplayer board, with an agent that reads the board and writes results back onto it. We cloned it because its "mini-apps" feature — an agent turns a text prompt into a real, interactive, persistent component on the canvas — is the same shape of problem as our Explore/iterate flow, and its canvas is a from-scratch engine that used to run on `@xyflow/react`, the library we're also built on. Both are worth reading closely for mechanism, not for adoption of the product as a whole: Dim0 is a multiplayer SaaS with a Postgres/Qdrant/Redis backend and cloud sandboxes; we are a local-only, single-player tool with zero footprint on the host and no server of our own beyond a Hono mount.

License: **MIT** (`LICENSE`, copyright 2026 vcmf). Read-only clone at the path given; nothing in it was modified for this research.

## Architecture

### Repo shape

```
backend/    FastAPI service (package name topix — legacy product name, still the module path/DB name)
webui/      React 19 + TS SPA — two domains: features/agent (chat/agent) and features/board (canvas)
build/      Docker Compose, schema.sql
docs/       architecture.md, features.md, roadmap.md — unusually current, worth reading over re-deriving
```

`docs/architecture.md` (68 lines) is a maintained, load-on-demand architecture doc the project itself keeps in sync with code — it explicitly says "verify against code before relying on a detail," which the notes below do.

### Canvas engine: migrated off `@xyflow/react`, confirmed

`webui/CLAUDE.md` states directly: *"`@canvas-harness/*` is an npm dependency, not in-tree source."* `webui/package.json` lists `@canvas-harness/core`, `@canvas-harness/react`, and `@canvas-harness/sync-broadcast` (all `^0.1.25`) as real dependencies — a separate library the same team maintains (`github.com/winlp4ever/canvas-harness`), not a vendored copy. `node_modules` isn't installed in this clone, so the harness's own rendering/gesture internals are **not inspectable from this repo** — only the consumer wiring is.

`@xyflow/react` is *also* still a listed dependency, which could read as an incomplete migration. It isn't: grepping the whole `webui/src` tree for `@xyflow/react` turns up exactly four files, and none of them render a `<ReactFlow>` component or call `useReactFlow` — the import is type-only or a single enum value in every case:

| File | Lines | What it imports from xyflow |
|---|---|---|
| `features/board/types/flow.ts` | 16 | `type Edge`, `type Node` — generic type aliases (`NoteNode = Node<NoteNodeData>`) |
| `features/board/utils/flow.ts` | 199 | `Position` (enum value, for Dagre handle placement), `type InternalNode`, `type Node` |
| `features/board/lib/graph/settings.ts` | ~40 | `Position` (enum value) |
| `features/board/store/viewport-store.ts` | 36 | `type Viewport` — shape for a `localStorage` cache, no xyflow runtime touched |

This is a real "types-only shim": the four files are a self-contained Dagre-based auto-layout module (`autoLayout`, used by `arrange-created-nodes.ts` to lay out mind-maps the agent just created) that predates the harness migration and still borrows xyflow's `Node<T>`/`Edge<T>` generic shapes and its `Position` enum because they're a convenient, already-typed vocabulary for a layout algorithm — not because any xyflow rendering code runs. Nothing in the live canvas path constructs a `ReactFlow` element. For us this means: if we ever wanted a similar clean split, keeping a dependency around purely for its type vocabulary in one isolated module, while the rendering path moves elsewhere, is precedented and doesn't have to mean "half-migrated."

### Where the weight lives

`webui/src/features/board/harness/canvas/harness-canvas.tsx` (570 lines) is the actual center of gravity — one `<Canvas>` mount per board, wiring in ~20 hooks (undo history-id rewriting, keyboard, viewport persistence, style memory, search indexing, doc-node cascade, presentation mode, theme projection, WS/offline-first sync, thumbnail capture) around a `CanvasStore` created once per component instance via `createBoardStore({ nodeTypes })`. It's a composition root, not business logic — each concern is a separate hook file under `harness/canvas/`, `harness/agent/`, `harness/persist/`, `harness/sync/`.

State management is two-layered:
- **`CanvasStore`** (from `@canvas-harness/core`) is the actual scene graph — nodes, edges, camera, selection, undo/redo — mutated exclusively through op batches (`store.applyBatch(...)`, ops like `node.add`/`node.update`/`edge.add`) carrying an `origin` tag (`"local"`, `"remote"`, `"history"`). This tagging is load-bearing throughout the codebase: `origin: "remote"` batches bypass both the undo stack and the debounced save loop (used for agent-written content, since the server already persisted it); `origin: "history"` batches are undo/redo replays.
- **Zustand** is used sparingly at the app-shell level (`board-app-store.ts`, 251 lines — `boardId`, `tool`, `viewMode`, `canEdit`, panel-open flags) — UI/session state, not scene state. Only 3 files in `features/board` import zustand at all; the scene itself is not a zustand store.

Two "mental models" the project's own docs call out as load-bearing and worth internalizing before touching the code:
1. **Two agent execution paths mid-cutover** — a legacy server-side agent (OpenAI Agents SDK, runs on the backend's own keys) and a newer browser-side tool-calling loop (`features/agent/engine/agent-loop.ts`) that mutates the canvas store directly and proxies external calls through metered `/ai/*` endpoints. The direction is: everything moves to the browser engine.
2. **Two persistence planes** — a REST/backend plane where the canvas-harness scene is converted to/from a `Note`/`Link` domain model (`harness/convert/`), and an "offline-first" plane where the harness scene *is* the model (no convert layer, IndexedDB via `features/board/persist/local/`). These are architecturally separate code paths, not two configurations of one path — don't conflate them when reading.

## Mechanisms behind features we might copy

### Mini-app runtime: source string → running component

This is the closest analog to what we do with generated variations, but built for a fundamentally different trust boundary (agent-authored code from an arbitrary end user, not a CLI you invoked yourself in your own repo).

**Compilation** (`webui/mini-app-runtime/compile.ts`, 155 lines): the agent writes one JSX source string via a `write_note(content_type="mini-app", ...)` tool call. `compileMiniApp(source, scope)` runs it through **sucrase** (`transform(source, { transforms: ["jsx","typescript"], jsxRuntime: "classic" })` — classic mode because there's no module system inside the eventual execution context, so `React.createElement` calls, not `react/jsx-runtime` imports, are required) then wraps the transpiled body in a `"use strict"` string and hands it to `new Function(...scopeNames, body)`, called with `scopeValues` positionally. The function body's own last line is a ternary that returns whichever of `Widget`/`App` the source defined at top level. Two distinct failure modes are surfaced as data, not exceptions: `kind: "compile"` (sucrase syntax error, or no `Widget`/`App` found) and `kind: "runtime"` (the top-level body threw when evaluated — e.g., referenced an out-of-scope identifier). Errors *inside* `Widget`'s own render are caught later, at actual render time, by a React error boundary, not by this function.

The **scope** the agent's code can reference is a single source-of-truth object, `MINI_APP_SCOPE` in `webui/mini-app-runtime/scope.ts` (170 lines): React + five hooks, five `Card*` components, `Button`, three chart/graph/map primitives, `cn`, and a `host` RPC object. Each entry carries both the runtime `value` and a `signature`/`doc` string; `renderScopeManifest()` renders the whole thing as markdown and that output is what's embedded in the agent's system prompt — so the allowlist the agent is told about and the allowlist actually wired into `new Function`'s parameter list can't drift apart, because they're generated from the same object.

**The sandbox** is not the `new Function` call — the code's own comment is explicit that `new Function` provides zero security by itself. The actual boundary is that the whole runtime is served from a **different origin** in production (`VITE_MINI_APP_ORIGIN`) or, in the "single-frontend" local-first build, loaded into an `<iframe sandbox="allow-scripts">` (no `allow-same-origin`) with `viteSingleFile` inlining everything into one static HTML file — the sandbox flag gives it an **opaque `null` origin**, so it has no parent DOM access, no host cookies, and every script/style fetch it makes is treated as cross-origin (hence the dev server's explicit `cors: { origin: "*" }`). The repo's own comment flags a real gap worth knowing about if this pattern is ever mimicked: the sandbox does **not** block network egress — a sandboxed opaque-origin iframe can still `fetch()` — closing that requires a CSP delivered via HTTP headers at the deploy layer, which isn't a repo asset.

**Tailwind inside the sandbox**: this is the one mechanism that's a direct, non-obvious answer to a problem we'd otherwise hit. The agent's JSX is a *string* at the point the outer app's `@tailwindcss/vite` plugin runs its static build — a static build can never see `className="fill-amber-200"` buried inside a string that gets `new Function`-evaluated at runtime, so those utility classes would simply never make it into any compiled CSS. Dim0's fix is `import "@tailwindcss/browser"` (a side-effect-only import in `main.tsx`) — Tailwind's JIT-in-the-browser build, which scans the *live DOM* after mount and generates the needed utility CSS on the fly. This only works because the mini-app is rendered in its own document (the iframe) where injecting a runtime stylesheet-generator is harmless; it would be a heavier, riskier thing to load into the *host* document.

**Host bridge** (`webui/mini-app-runtime/rpc.ts`, 132 lines): a tiny request/response protocol over `postMessage`. Every `host.*` call (`saveState`, `toast`) posts `{ type: "mini-app:rpc", id, method, args }` to `window.parent` and returns a `Promise` that resolves when a `{ type: "mini-app:rpc-result", id, result|error }` arrives; a `Map<id, {resolve,reject}>` tracks in-flight calls. `host.initialState` is the one non-method surface — set synchronously by the runtime entry, from the `mini-app:render` payload, before the compiled `Widget` is invoked, so a `useState(host.initialState ?? default)` on first render reads the right value. Auto-resize works the same way in reverse: a `ResizeObserver` on `document.body`, rAF-coalesced, posts `{ type: "mini-app:resize", height }` on every content-size change; the host's node view batches those into at most one `store.updateNode(id, {h})` per animation frame and only ever **grows** the card (shrinking stays a manual user action via the resize handle) — capped at 1200px so a runaway widget can't monopolize the board.

**What this buys them that inline rendering doesn't**: genuine isolation of agent-authored code from the host's DOM, cookies, and (mostly) network — worth it because their agent output is untrusted relative to the *end user's own account and data*, running on a server they operate for many tenants. It costs them: a second Vite build target (`vite.mini-app.config.ts`, 2 dev servers in dev), a hand-rolled RPC protocol for every capability the widget needs (state, toasts — anything else is a new `host.*` method and a new message type), and no ability for the widget to interact with anything else on the board (drag, select, alt-hover) the way our inline previews can.

### Canvas interaction model: keeping interactive content from stealing canvas gestures

We have almost exactly this problem with live component previews, so this is the most directly transferable finding. `webui/src/features/board/harness/node-types/mini-app/view.tsx` (158 lines) gates the mini-app iframe's `pointer-events` on **selection state**, not on any richer interaction-mode toggle:

```tsx
const selection = useSelection()
const isSelected = selection.includes(id)
...
<MiniAppMount
  className={cn("h-full w-full bg-transparent",
    isSelected ? "pointer-events-auto" : "pointer-events-none")}
  ...
/>
```

The comment in that file states the failure mode plainly: without this, "the iframe's `pointer-events-auto` captures the pointer the moment the user's drag crosses into the card → canvas-harness loses gesture tracking → pan dies mid-swipe." The outer wrapper div is also `pointer-events-none` by default, with only the traffic-lights row and the title caption opted back in via `pointer-events-auto` on those specific elements. The comment cross-references that the sheet node type's inline text editor uses the identical pattern but gates on `editing` instead of `selection` — so the codebase has a named, repeated idiom ("gate interactive content's pointer-events on the mode that means the user intends to interact with *this specific node*") rather than one-off fixes per node type. Our `data-pg-interact-catcher` transparent-div-until-double-click pattern is solving the same class of problem with a different trigger (explicit double-click enter vs. implicit selection); worth knowing there's a viable alternative trigger already proven at scale here, in case double-click ever turns out to be the wrong UX in some context.

The rest of the canvas gesture engine itself — panning, actual pointer capture, hit-testing internals (`hitTestAny`, imported and used but not defined here) — lives inside `@canvas-harness/core`, out of tree and not inspectable from this clone. Only the consumer-side wiring (`onCreateDrag`, `onClick`, `onDoubleClick` callbacks passed to `<Canvas>`) is visible.

### Undo/redo and persistence

Undo/redo itself is a `@canvas-harness/core` primitive (`store.applyBatch`, `inverseBatch`, batches tagged `origin: "history"`) — the mechanism is out of tree and not verifiable from this repo. One real gotcha Dim0's own code documents (`harness/canvas/use-history-batch-ids.ts`): the harness's `redo()` re-applies the *original* batch with its *original* id (only `undo()` mints a fresh one), which silently breaks a persisted/synced log — the oplog's dedup-by-id treats the redo as an already-seen replay and drops it, and the relay does the same. Dim0's fix is a subscriber that rewrites the id on every `origin: "history"` batch before persistence/collab hooks see it. This is a good concrete warning if we ever build undo on top of a library whose redo semantics we don't fully control: check whether redo reuses the undo'd batch's identity, because anything keyed by batch id downstream (a log, a dedup set) will misbehave.

Persistence genuinely differs by which of the two planes a board is on:

| | Legacy REST plane | Offline-first (v2) plane |
|---|---|---|
| Unit of persistence | Full-scene **snapshot diff** | **Operation log** (oplog) |
| Mechanism | `diffSnapshots(prev, next)` (`harness/persist/diff-snapshots.ts`, 127 lines) — `JSON.stringify` equality per node/edge, id-set difference for adds/removes, produces `ApiCall[]` (`addNote`/`updateNote`/`removeNote`/…), flushed via debounce | Every local op batch is written to an IndexedDB `oplog` table; the "outbox" isn't a separate queue, it's just the oplog tail past a persisted `syncedSeq` cursor (`persist/local/board-outbox.ts`) |
| What's coalesced | Nothing explicit — a debounce window collects edits, then one diff pass computes the minimal call set for that window (multiple edits to one node still net out to one `updateNote`) | Batches within a `coalesceMs` window are concatenated (`ops.flatMap`) into one outbound relay message; a follow-on `enrichOutbound` hook dedupes repeat-same-target ops so a drag/rotate flood (one op per pointermove) collapses to one op per node before it's sent |
| What's ignored | — | Server explicitly does NOT persist `group.*` / `frame.reorder` ops — relayed live to peers but dropped from the durable log |
| Conflict resolution | Last-writer-wins by whichever REST call lands last (no explicit ordering) | Server-sequenced per-field LWW via **rebase**: on a remote op, undo every locally-unacked batch (in reverse), apply the remote op onto that confirmed base, replay the local batches back on top — so a local edit always ends up ordered after everything it hasn't yet been sequenced against. A referential-integrity pass then drops any edge left dangling by a concurrent node delete on the other side. |
| Cascade behavior | Node geometry changes cascade an `updateLink` resave for any attached "legacy" edge (one whose position was stored in world coordinates) so it doesn't go stale, and upgrades it to a newer local-offset format in the same pass | — |

The offline-first plane (`harness/sync/board-sync.ts`, 364 lines) is considerably more machinery than we'd ever need — it exists because Dim0 has real multiplayer over an unreliable WebSocket. The idea worth taking, if we ever needed conflict-free coalescing of a burst of edits (e.g. a drag gesture) before writing to `localStorage`, is the batch-merge-then-dedupe shape (`mergeBatches` → `enrichOutbound`), not the rebase/LWW machinery, which only matters once there's more than one writer.

### Prompt structure and parsing agent output back into canvas state

The mini-app skill prompt (`backend/topix/prompts/widget/learn_generate_mini_app.jinja`, 435 lines) is one long, single-purpose system-prompt fragment with a specific structure: a "SKILL (high priority)" banner asserting precedence over generic habits, an exact contract section ("write **one** JSX source string... the runtime compiles it via sucrase and renders the component named `Widget`"), an explicit "Strict rules — these always reject" list naming forbidden globals (`window`, `document`, `fetch`, `eval`, …) and import statements, a scope section that is **generated from the same `MINI_APP_SCOPE` object** the runtime actually wires up (so the prompt can't drift from what's really available), eight fully worked JSX examples covering each primitive (counter, todo list, stepper, three chart/graph variants, a manual-layout algorithm visualizer, a choropleth map), then style/typography/color guidance, and a closing "Verification before you submit" checklist the agent is told to walk through before calling the tool. A sibling, explicitly deprecated prompt (`learn_generate_html_widget.jinja`) exists for a legacy raw-HTML-in-iframe note type and opens by telling the agent to prefer the mini-app skill instead — a visible, in-prompt migration note rather than a silent one.

Agent output reaching the canvas is a **two-hop, fetch-back** design, not a direct apply of whatever the tool call returned: the browser-side tool-call handler gets back only an identifier (`{ noteId, graphUid }` from `write_note`/`create_note`/`edit_note`); `applyNoteOutput` (`harness/agent/apply-tool-output.ts`, 129 lines) then does a **fresh REST fetch of the canonical `Note`** by that id, converts it to a harness `Node` via the existing convert layer (the same one persistence uses), and applies it as a single `origin: "remote"` op batch — which, per the origin-tagging convention above, bypasses both the undo stack and the debounced-save loop, because the server already has the authoritative copy. If the note's `parentId` doesn't match the currently-viewed board layer, no node is materialized on the visible canvas at all — only the React Query cache is refreshed, so an already-open panel elsewhere still sees the edit. One further pass, `arrangeCreatedNodes` (`harness/agent/arrange-created-nodes.ts`, 218 lines), runs after a multi-node agent turn: without it, every note the agent just wrote lands at `(0,0)` and a generated mind-map collapses to a single point, so this function classifies the newly-created subgraph as a tree (or falls back to flat Dagre), lays it out (a hand-written "centered bidirectional mindmap" layout — split the root's children left/right by subtree weight, Dagre each half, mirror and stitch), and translates the whole cluster to sit just below existing board content in one local batch.

### Overlay/portal containment

No dedicated solution was found. Grepping the whole `features/board` tree for Radix `Portal`/`container` usage turns up nothing related to node cards — Dialog/Sheet-shaped Radix components in this codebase are only used as top-level app chrome (the slides panel, settings), never rendered live *inside* a canvas node. The mini-app runtime sidesteps the problem entirely rather than solving it: because mini-app content renders inside its own iframe document, anything the agent's code portals (there's no Dialog primitive in its allowed scope anyway) would portal within that iframe's own DOM, not escape into the host document. The legacy HTML-widget note type is iframed too. In other words: Dim0 never had to solve "contain an escaping Radix overlay inside a transformed, overflow-hidden card," because everything that could produce one is isolated behind an iframe boundary by construction. This confirms rather than contradicts our own CLAUDE.md rule (no Dialog/Sheet-shaped components in the live-preview registry) — it's the same problem, solved by them via a boundary we've deliberately chosen not to introduce.

## What they do that we deliberately won't, and why

**Iframe-sandboxed execution for generated UI.** This is the mechanism most tempting to borrow wholesale, and the one most wrong for us specifically. Our element-selection model (`useElementSelection.ts` + `extractElementContext`) is plain DOM traversal against the live, same-document render tree — alt+hover/click walks real DOM nodes and reads real computed styles. An iframe boundary makes that impossible without rebuilding it as a cross-frame RPC bridge, which is exactly the `penpal` dependency our own architecture notes record as *removed*. Dim0 needs the boundary because its agent output is untrusted relative to a paying end user's own account, data, and cookies, running on infrastructure they operate for many tenants at once. Our "untrusted" surface is Claude Code, invoked by the same developer, in the same local repo, writing files the developer can already read and run directly — there is no cross-tenant trust boundary to defend, so the isolation buys us nothing and costs us our whole selection model.

**Cloud-shaped infrastructure throughout.** Code execution runs in Daytona-backed cloud sandboxes (`DAYTONA_API_KEY`/`DAYTONA_API_URL` in `.env.sample`, `backend/topix/agents/assistant/code.py`); all board content — notes, links, documents, chunks — lives in one Qdrant collection; Postgres holds relational metadata and the collab oplog; Redis holds WS tickets and the live seq counter; a WebSocket relay plus the rebase/LWW machinery in `board-sync.ts` exists to make real-time multiplayer converge. Every one of these is there to serve a multi-tenant, multiplayer, always-online product. We are explicitly local-dev-only, single-player, with no database and no server process beyond a Hono app mounted into the host's existing Vite dev server — none of this has a use for us, and copying any piece of it (a "just in case" Postgres table, a "just in case" WS relay) would be pure footprint against a product that has zero users to synchronize between.

**Bring-your-own-model across six providers.** Dim0's agent layer resolves models through a YAML catalog (`backend/topix/config/catalog.py` over `models.yml`) supporting OpenAI, Anthropic, Gemini, Mistral, Moonshot, DeepSeek, Qwen, Z.ai, with keys either sent BYOK-direct from the browser or relayed per-request. Our multi-provider seam is gone by design — Claude Code is the only agent, and the abstraction Dim0 needs to keep six providers interchangeable (a routing table, a `ProviderId`-shaped catalog, provider-specific key handling) is exactly the kind of thing our own CLAUDE.md flags as deliberately removed (`providers/` directory, `ProviderId` type, `DEFAULT_PROVIDER_ID`).

**A backend service with its own database and auth.** Dim0's `backend/` is a full FastAPI service with Postgres/Qdrant/Redis, JWT auth, billing/plan-gated rate limiting, and email flows (Resend, for verification and password reset) — a real multi-user product backend. We have no accounts, no billing, and are explicitly barred from adding anything to the host's `package.json` or standing up a server process of our own; the entire backend surface Dim0 needs for "who is this user, what can they do, how much have they used" has no analog in a single-developer local tool.
