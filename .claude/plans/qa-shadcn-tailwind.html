Paths: cwd & playground-root

What does cwd mean?

Current working directory — the folder the host process was started from (usually the host app root when you run bun dev). Server code uses process.cwd() as “where is the project on disk?”

Done

What does playground root do?

Hosts install at either src/app/playground or app/playground. Vite plugin resolves that once and injects __PG_RELATIVE_ROOT__ into the client — prompts use the right disk path with no HTTP. The old /api/playground-root route is gone.

Discovered registry (why three?)

Three pieces, one pipeline

  • discovered-registry.json — data only (ids, import paths, props). Safe to write.
  • discovered-registry.gen.tsx — generated imports Vite can HMR. JSON can’t hold live components.
  • registry.tsx — runtime API (subscribe, resolve, preload) + HMR accept of the .gen file.

Writers: server/lib/discovered-registry.ts. Today static scan doesn’t write the JSON yet — that’s the unfinished Phase‑2 wire.

Done

RegistryDragRow (was ComponentPreviewCard)

PascalCase component + file — drag row, not a preview card.

Why JSX stamp?

data-pg-src="file:line:col"

Alt‑select today guesses what you clicked (DOM walk + React fiber names). That’s brittle (forwardRef, wrappers, wrong labels).

A Vite transform stamps origin onto each JSX element as it’s served — never written to host git. Selection becomes “read the attribute,” and prompts get real anchors. We skip Onlook’s approach of rewriting your source files.

Still planned — measure HMR cost before committing.

Relations & visibility

canvas-relations vs canvas-visibility

Relations = parent→child links between canvas nodes (which variation came from which). Not drawn as edges — just the family tree.

Visibility = when you collapse a parent, hide its descendants.

Future: layers panel sync, “collapse branch,” cascade delete, auto-arrange by tree, and (later) a source render-tree that mirrors the same shape.

Paste: two files

canvas-paste.ts vs useCanvasPaste.ts

canvas-paste.ts = pure “what is on the clipboard?” → image or nothing. No React, no upload.

useCanvasPaste.ts = listens for paste, uploads the image, drops an ImageNode at viewport center.

Split so the decision is testable without mocking the DOM.

How a component lands on canvas

Iframe?

No. Drag → useCanvasDragDrop creates a React Flow ComponentNode → it renders the host component inline in the same document via the registry’s live import.

data-iframe-overlay is a legacy name for a transparent click-catcher (block links until double-click “interact”). Not a real iframe. That’s why Radix portals escape the card — they’re in the same document.body.

useCanvasFrameOps vs FrameNode

FrameNode = the visual group box on the canvas (a node type).

useCanvasFrameOps = the behaviors: group selection into a frame, ungroup, z-order, alignment helper lines, context-menu wiring.

One is the thing; the other is the verbs.

Sticky text notes (TextNode)?

A canvas node you place with the text tool (toolbar). Editable sticky copy. When you @-reference it in chat, its text is injected into the prompt as a reference — hence “prompt refs.” Easy to miss if you never used the text tool.

Prompts & fill-template

Why four explore prompts?

  • From source component
  • From an existing iteration
  • Same two, but scoped to an Alt-selected element

Plus separate templates for edit, freeform, and adopt. That’s why the folder feels fat.

Leaner approach: one explore template with flags (fromIteration, elementSelections) assembled in prompt-builders.ts — delete duplicate template files once the shared sections cover the differences. Keep adopt with iterations (already moved).

fill-template.ts: agree it’s too thin as a solo file. Inline {{key}} replace next to the builders, or a private helper in prompt-builders.ts / adopt-prompt.ts — don’t keep a dedicated module for 8 lines.

Lifecycle & coordination (SSE, mutex)

In plain English

  • Coordination (useGenerationCoordination) — “is something generating?”, what was requested, latest nodes list. Shared blackboard so scan + lifecycle + chat don’t fight.
  • Mutex / scan lock — only one “look for new iteration files” pass at a time; if another ask arrives mid-scan, queue one more. Prevents double-placing the same card.
  • Lifecycle (useGenerationLifecycle) — on start: drop skeleton cards; subscribe to progress; on complete/error: final scan + cleanup.
  • SSE — server watches Claude’s tool stream, pushes “file written” events; browser updates without waiting for the whole job.
  • Two buses — server SSE ≠ client generationEvents (start/complete/error inside the React app). Different jobs, similar names on purpose after rename.
